<a id="to-panic-or-not-to-panic"></a>

## 该不该使用 `panic!`

那么，如何判断何时应该调用 `panic!`，何时应该返回 `Result` 呢？代码 panic 后便无法恢复。任何错误情况下都可以调用 `panic!`，无论是否有可能恢复；但这样做就等于替调用代码决定了该情况不可恢复。选择返回 `Result` 值，则会给调用代码留下选择余地。调用代码可以尝试以适合其情形的方式恢复，也可以判断此时的 `Err` 值不可恢复，再调用 `panic!`，把可恢复错误变为不可恢复错误。因此，在定义可能失败的函数时，返回 `Result` 是一个很好的默认选择。

在示例、原型代码和测试等场景中，编写会 panic 的代码比返回 `Result` 更合适。让我们探究其中的原因，再讨论编译器无法判断失败不可能发生、但人类可以判断的情况。本章最后会给出一些通用准则，帮助你决定是否在库代码中触发 panic。

### 示例、原型代码和测试

编写用于说明某个概念的示例时，如果还加入健壮的错误处理代码，示例可能反而不够清晰。在示例中，调用 `unwrap` 这类可能 panic 的方法，通常被理解为实际应用中错误处理方式的占位符；具体处理方式会因其余代码的行为而异。

类似地，在编写原型、尚未准备好决定如何处理错误时，`unwrap` 和 `expect` 方法非常方便。它们会在代码中留下清晰的标记，提醒你在准备增强程序健壮性时回来处理这些位置。

如果测试中的某个方法调用失败，即使该方法并不是被测试的功能，你也会希望整个测试失败。由于测试通过 `panic!` 被标记为失败，调用 `unwrap` 或 `expect` 正是应有的做法。

<a id="guidelines-for-error-handling"></a>

### 错误处理准则

如果代码可能进入<em>错误状态(bad state)</em>，建议让代码 panic。在此语境中，错误状态指某项假设、保证、契约或不变量遭到破坏，例如向代码传入无效值、相互矛盾的值或缺失的值，并且还符合以下一项或多项条件：

- 这种错误状态出乎意料，而不像用户以错误格式输入数据那样可能偶尔发生。
- 此后的代码需要依赖于没有处于这种错误状态，而不是在每一步都检查问题。
- 没有合适的方法把这些信息编码到所使用的类型中。第 18 章[“将状态和行为编码为类型”][encoding]会通过一个例子说明其含义。

如果有人调用你的代码并传入不合理的值，最好在可行时返回错误，让库的使用者决定如何处理。不过，如果继续执行可能不安全或造成危害，最佳选择可能是调用 `panic!`，提醒库的使用者其代码中存在 bug，以便在开发期间修复。类似地，如果调用不受你控制的外部代码，而它返回了你无法修复的无效状态，通常也适合使用 `panic!`。

不过，当失败属于预期情况时，返回 `Result` 比调用 `panic!` 更合适。例如，解析器收到格式错误的数据，或者 HTTP 请求返回表示已触及速率限制的状态。在这些情况下，返回 `Result` 表明失败是一种预期的可能性，调用代码必须决定如何处理。

如果代码执行的操作在接收到无效值时可能使用户面临风险，就应该先验证值是否有效，并在无效时 panic。这主要是出于安全原因：尝试操作无效数据可能使代码暴露出漏洞。这也是标准库在你尝试越界访问内存时调用 `panic!` 的主要原因：试图访问不属于当前数据结构的内存是一种常见安全问题。函数通常带有<em>契约(contract)</em>：只有输入满足特定要求时，才保证函数的行为。违反契约时触发 panic 是合理的，因为契约违规始终意味着调用方存在 bug，也不是一种应该要求调用代码显式处理的错误。事实上，调用代码没有合理的恢复方式，需要修复代码的是调用方的<em>程序员</em>。函数的契约，尤其是违反契约会导致 panic 时，应在函数的 API 文档中说明。

不过，在所有函数中加入大量错误检查会既冗长又烦人。幸运的是，可以利用 Rust 的类型系统（从而利用编译器执行的类型检查）替你完成许多检查。如果函数有一个特定类型的参数，就可以继续执行代码逻辑，因为编译器已经确保你获得了有效值。例如，如果参数是某个类型而不是 `Option`，程序就预期得到<em>某个值</em>，而不是<em>没有值</em>。代码不必再处理 `Some` 和 `None` 两种情况，只需处理确定存在值的一种情况。试图不传值给该函数的代码甚至无法编译，所以函数无需在运行时检查这种情况。另一个例子是使用 `u32` 这样的无符号整数类型，它能确保参数永远不会为负数。

### 用于验证的自定义类型

让我们进一步运用 Rust 类型系统确保值有效的思路，看看如何创建用于验证的自定义类型。回想第 2 章的猜数字游戏，代码要求用户猜一个 1 到 100 之间的数字。在把猜测值与秘密数字比较之前，我们从未验证用户的猜测是否位于这个范围，只验证了猜测值是正数。在这种情况下，后果并不严重：输出“Too high”或“Too low”仍然正确。不过，引导用户输入有效猜测会是一项有用的改进；当用户猜测超出范围的数字时，程序也可以表现得不同于用户输入字母等内容时的情况。

接着，我们在 `Guess` 上实现名为 `new` 的关联函数，用于创建 `Guess` 值的实例。`new` 函数定义了一个名为 `value`、类型为 `i32` 的参数，并返回 `Guess`。`new` 的函数体会检查 `value`，确保它位于 1 到 100 之间。如果 `value` 未通过检查，就调用 `panic!`，提醒编写调用代码的程序员：其代码中有需要修复的 bug，因为创建 `value` 不在这个范围内的 `Guess` 会违反 `Guess::new` 所依赖的契约。`Guess::new` 可能 panic 的条件应该在面向公众的 API 文档中讨论；第 14 章会介绍如何在你创建的 API 文档中按照约定标明 panic 的可能性。如果 `value` 通过检查，就创建一个新的 `Guess`，把其 `value` 字段设为参数 `value`，然后返回该 `Guess`。

然后，我们实现名为 `value` 的方法，它借用 `self`，没有其他参数，并返回 `i32`。这种方法有时称为<em>获取器(getter)</em>，因为其用途是从字段中取得一些数据并返回。这个公有方法是必要的，因为 `Guess` 结构体的 `value` 字段是私有的。让 `value` 字段保持私有非常重要，这样使用 `Guess` 结构体的代码就不能直接设置 `value`：`guessing_game` 模块之外的代码<em>必须</em>使用 `Guess::new` 函数创建 `Guess` 实例，从而确保绝不可能出现其 `value` 未经 `Guess::new` 函数条件检查的 `Guess`。

如果一个函数的参数或返回值只能是 1 到 100 之间的数字，就可以在签名中声明它接收或返回 `Guess` 而不是 `i32`，函数体中也无需进行任何额外检查。

## 总结

Rust 的错误处理功能旨在帮助你编写更加健壮的代码。`panic!` 宏表明程序进入了无法处理的状态，让你停止进程，而不是尝试带着无效或错误的值继续执行。`Result` 枚举利用 Rust 的类型系统来表明操作可能以代码可恢复的方式失败。你可以使用 `Result` 告知调用代码，它需要处理潜在的成功或失败。在适当的情况下使用 `panic!` 和 `Result`，能让代码在面对不可避免的问题时更加可靠。

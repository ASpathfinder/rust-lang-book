# 异步编程基础：Async、Await、Future 与 Stream

我们要求计算机执行的许多操作都可能需要一段时间才能完成。如果在等待这些耗时进程结束时还能做些别的事情，那就很好了。现代计算机提供了两种同时处理多项操作的技术：并行和并发。然而，程序逻辑大多仍以线性方式编写。我们希望能够指定程序应执行哪些操作，以及函数可在哪些位置暂停、转而运行程序的其他部分，而不必预先明确规定每段代码运行的确切顺序和方式。<em>异步编程(asynchronous programming)</em>是一种抽象，让我们可以用潜在暂停点和最终结果来表达代码，并替我们处理协调细节。

第 16 章使用线程实现并行与并发，本章将在此基础上介绍另一种代码编写方式：Rust 的 future、stream 以及 `async` 和 `await` 语法，用它们表达操作如何异步执行；还会介绍实现异步运行时的第三方 crate，异步运行时是管理和协调异步操作执行的代码。

考虑一个例子。假设你正在导出一段自己制作的家庭庆典视频，这项操作可能耗时几分钟到几小时。视频导出会尽可能多地使用 CPU 和 GPU 算力。如果只有一个 CPU 核心，且操作系统在导出完成前不会暂停它，也就是说，导出以<em>同步(synchronously)</em>方式执行，那么在这项任务运行期间，你无法在计算机上做任何其他事情。这会是一种相当令人沮丧的体验。幸运的是，计算机的操作系统能够而且确实会在幕后频繁中断导出，让你同时完成其他工作。

现在假设你正在下载别人分享的视频，这同样可能需要一段时间，但不会占用那么多 CPU 时间。在这种情况下，CPU 必须等待数据从网络到达。数据开始到达后就能着手读取，但全部数据到齐可能还需要一些时间。即使所有数据都已到达，如果视频很大，完整加载它至少也可能需要一两秒。听起来或许不长，但对于每秒可执行数十亿次操作的现代处理器来说，这是非常漫长的时间。操作系统同样会在幕后中断程序，让 CPU 在等待网络调用结束时执行其他工作。

视频导出是 <em>CPU 密集型(CPU-bound)</em>或<em>计算密集型(compute-bound)</em>操作的例子。它受限于计算机在 CPU 或 GPU 中可能达到的数据处理速度，以及能够为该操作投入多少处理能力。视频下载则是 <em>I/O 密集型(I/O-bound)</em>操作的例子，因为它受限于计算机<em>输入和输出(input and output)</em>的速度；其速度不可能超过数据通过网络传输的速度。

在这两个例子中，操作系统的幕后中断都提供了某种并发。不过，这种并发只发生在整个程序的层面：操作系统中断一个程序，让其他程序完成工作。在许多情况下，我们对自己程序的理解粒度远比操作系统更细，因此能发现操作系统看不到的并发机会。

例如，如果正在构建一个管理文件下载的工具，应当能够让程序启动一次下载而不锁死 UI，并让用户可以同时启动多次下载。然而，许多与网络交互的操作系统 API 都是<em>阻塞式(blocking)</em>的，也就是说，它们会阻止程序继续执行，直到所处理的数据完全就绪。

> 注意：仔细想想，<em>大多数</em>函数调用都是这样工作的。不过，“阻塞”一词通常专门用于与文件、网络或计算机上其他资源交互的函数调用，因为在这些场景中，让操作<em>非</em>阻塞会给单个程序带来好处。

可以通过为每个文件生成一个专用下载线程，避免阻塞主线程。然而，这些线程所使用系统资源的开销最终会成为问题。如果调用从一开始就不阻塞会更理想：我们可以定义希望程序完成的一系列任务，再让运行时选择执行它们的最佳顺序和方式。

这正是 Rust 的 <em>async</em>（<em>asynchronous</em> 的缩写）抽象所提供的能力。本章将全面介绍 async，涵盖以下主题：

- 如何使用 Rust 的 `async` 和 `await` 语法，并用运行时执行异步函数
- 如何使用异步模型解决第 16 章中见过的一些相同挑战
- 多线程与 async 如何提供互补方案，并在许多情况下结合使用

不过，在实际了解 async 的工作方式之前，需要稍作绕行，讨论并行与并发的区别。

## 并行与并发

到目前为止，我们基本把并行和并发视为可以互换的概念。现在需要更精确地区分它们，因为开始实践后，这些区别会显现出来。

想想一个团队分配软件项目工作的不同方式。可以给一名成员分配多项任务，也可以给每名成员各分配一项任务，还可以混合采用这两种方法。

当一个人在几项任务都尚未完成时交替处理它们，这就是<em>并发(concurrency)</em>。实现并发的一种方式，类似于在计算机上签出两个不同项目：当你对一个项目感到厌烦或陷入困境时，就切换到另一个项目。因为只有你一个人，无法在完全相同的时刻推进两项任务，但可以进行多任务处理，在任务间切换，每次推进其中一项（见图 17-1）。

在这两种工作流中，都可能需要协调不同任务。也许你原以为分配给某个人的任务完全独立于其他人的工作，实际上却必须等团队中另一人先完成任务。部分工作可以并行进行，但另一部分其实是<em>串行(serial)</em>的：它只能按顺序发生，一项任务接着另一项任务，如图 17-3 所示。

<figcaption>图 17-3：部分并行的工作流；任务 A 和任务 B 各自独立推进，直到任务 A3 因等待任务 B3 的结果而被阻塞。</figcaption>

</figure>

同样，你可能发现自己的一项任务依赖自己的另一项任务。此时，并发工作也变成了串行工作。

并行和并发也可能相互交织。如果得知同事在你完成某项任务前无法继续，你很可能会把全部精力集中到该任务上，以“解除”同事的阻塞。你和同事不再能够并行工作，你自己也不再能够并发处理多项任务。

软件和硬件中也存在相同的基本动态。在只有一个 CPU 核心的计算机上，CPU 一次只能执行一项操作，但仍然可以并发工作。借助线程、进程和 async 等工具，计算机可以暂停一项活动并切换到其他活动，最终再循环回来继续第一项活动。在拥有多个 CPU 核心的计算机上，它还能并行工作。一个核心可以执行一项任务，同时另一个核心执行完全不相关的任务，这些操作确实会同时发生。

在 Rust 中运行异步代码通常以并发方式进行。根据硬件、操作系统以及所使用的异步运行时（很快会进一步介绍），这种并发在底层也可能利用并行。

现在，让我们深入了解 Rust 中的异步编程究竟如何工作。

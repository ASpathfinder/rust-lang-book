## 融会贯通：Future、任务与线程

正如[第 16 章][ch16]<!-- ignore -->所见，线程提供了一种并发方法。本章又介绍了另一种方法：配合 future 和 stream 使用 async。如果你想知道何时应该选择其中一种方法，答案是：视情况而定！而且在许多情况下，选择并不是线程<em>或</em> async，而是线程<em>和</em> async。

数十年来，许多操作系统一直提供基于线程的并发模型，许多编程语言也因此支持它们。不过，这些模型并非没有权衡。在许多操作系统上，每个线程都会使用相当多的内存。线程也只有在操作系统和硬件支持时才可用。与主流桌面和移动计算机不同，一些嵌入式系统根本没有操作系统，因而也没有线程。

异步模型提供了一组不同且最终相互补充的权衡。在异步模型中，并发操作不需要自己的线程，而是可以在任务上运行，就像 stream 一节中使用 `trpl::spawn_task` 从同步函数启动工作那样。<em>任务(task)</em>类似于线程，但它不由操作系统管理，而由库级代码（即运行时）管理。

生成线程和生成任务的 API 如此相似，是有原因的。线程充当一组同步操作的边界，并发可以发生在<em>线程之间</em>。任务充当一组<em>异步</em>操作的边界，并发既能发生在<em>任务之间</em>，也能发生在<em>任务内部</em>，因为任务可以在其函数体中的多个 future 之间切换。最后，future 是 Rust 最细粒度的并发单元，每个 future 都可能代表由其他 future 构成的一棵树。运行时（确切地说，是其执行器）管理任务，而任务管理 future。就此而言，任务类似由运行时管理的轻量级线程；由于由运行时而非操作系统管理，它还拥有额外能力。

这并不意味着异步任务总是优于线程（反之亦然）。在某些方面，使用线程实现并发是比使用 `async` 更简单的编程模型。这既可能是优点，也可能是缺点。线程在一定程度上是“触发后即不再过问”的；它们没有 future 的原生等价物，因此除了被操作系统本身中断外，只会直接运行到完成。

事实证明，线程与任务经常能很好地协同工作，因为任务（至少在某些运行时中）可以在线程之间移动。实际上，我们一直使用的运行时，包括 `spawn_blocking` 和 `spawn_task` 函数，在底层默认就是多线程的！许多运行时采用一种称为<em>工作窃取(work stealing)</em>的方法，根据线程当前的利用情况，在不同线程之间透明地移动任务，以提高系统整体性能。这种方法实际上同时需要线程<em>和</em>任务，因而也需要 future。

思考何时使用哪种方法时，可以参考以下经验法则：

- 如果工作<em>非常适合并行化</em>（也就是 CPU 密集型），例如处理一批可以分别处理各部分的数据，线程是更好的选择。
- 如果工作<em>高度并发</em>（也就是 I/O 密集型），例如处理来自许多不同来源、可能以不同间隔或不同速率到达的消息，async 是更好的选择。

如果既需要并行又需要并发，不必在线程与 async 之间二选一。可以自由地结合使用两者，让它们各自发挥最擅长的作用。例如，示例 17-25 展示了现实 Rust 代码中相当常见的一种混合方式。
